# Изменение frontend-функциональности

Используй этот skill при реализации новой frontend-функциональности или изменении существующей функциональности проекта.

## 1. Сначала изучи существующий код

Перед внесением изменений:

- найди страницу или компонент, к которому относится задача;
- изучи связанные компоненты;
- изучи используемые типы;
- проверь существующую маршрутизацию, если задача связана со страницами или переходами;
- изучи существующий подход к стилизации;
- проверь, есть ли уже компонент или логика, которые можно переиспользовать;
- проверь похожие реализации в других частях проекта.

Не начинай решение задачи с создания новых абстракций.

Сначала постарайся понять, как аналогичные задачи уже решаются в этом проекте.

## 2. Определи область изменений

Перед реализацией определи:

- какие файлы необходимо изменить;
- потребуется ли создавать новые файлы;
- затрагивается ли маршрутизация;
- затрагиваются ли общие компоненты;
- изменяется ли структура данных;
- требуется ли новое состояние;
- влияет ли изменение на другие части приложения.

Старайся минимизировать область изменений.

Не изменяй файлы, которые не относятся к текущей задаче.

## 3. Составь план

Для задач, затрагивающих несколько файлов или имеющих нетривиальную логику, сначала кратко опиши предполагаемую реализацию.

План должен объяснять:

- что будет изменено;
- какие компоненты будут затронуты;
- где будет находиться состояние;
- как будут передаваться данные;
- потребуется ли изменение маршрутизации;
- потребуется ли создание нового компонента;
- какие существующие компоненты можно переиспользовать.

Не создавай чрезмерно подробный план для маленькой и очевидной задачи.

## 4. Реализация

При реализации используй существующий стек проекта:

- React;
- TypeScript;
- Material UI;
- React Router;
- Vite;
- существующую архитектуру и структуру проекта.

Предпочитай самое простое решение, которое соответствует текущей архитектуре.

Не добавляй новую библиотеку, если задача решается существующими средствами проекта.

## 5. React-компоненты

Используй функциональные React-компоненты и Hooks.

Компонент должен иметь понятную ответственность.

Если компонент становится слишком большим, сначала определи, действительно ли часть логики можно разумно вынести.

Не разбивай маленькие компоненты на множество файлов только ради формального уменьшения размера.

Предпочитай переиспользование существующего компонента вместо создания почти такого же нового.

Не используй `useEffect`, если значение можно вычислить непосредственно из `props` или `state`.

Если создаётся внешний ресурс, например:

- event listener;
- timer;
- subscription;
- WebSocket;

обязательно проверь необходимость cleanup.

## 6. State

Перед добавлением состояния определи, действительно ли оно необходимо.

Не создавай отдельный state для значения, которое можно вычислить из другого state или props.

Локальное состояние компонента оставляй локальным, если другим частям приложения оно не требуется.

Не переносись автоматически в глобальное состояние только ради возможности получить значение из другого компонента.

Не создавай несколько источников истины для одних и тех же данных.

## 7. TypeScript

Не используй `any` без веской причины.

Если значение неизвестно, предпочитай `unknown` и выполняй narrowing перед использованием.

Используй существующие типы проекта, если они уже описывают нужную сущность.

Не создавай несколько почти одинаковых типов.

При необходимости используй:

- `Pick`;
- `Omit`;
- `Partial`;
- `Record`;
- union types;
- discriminated unions.

Не скрывай проблемы типизации через необоснованный `as`.

Если TypeScript показывает проблему, сначала выясни её причину.

## 8. Material UI

Перед созданием собственного UI-компонента проверь, существует ли подходящий компонент Material UI или проекта.

Сохраняй существующий визуальный стиль приложения.

Используй уже существующие:

- размеры;
- spacing;
- typography;
- компоненты;
- варианты кнопок;
- цвета;
- layout-паттерны.

Не подключай дополнительный UI framework без явного требования.

Не заменяй существующие Material UI-компоненты кастомными аналогами без причины.

## 9. Адаптивность

После UI-изменений проверь поведение интерфейса как минимум на:

- desktop;
- tablet, если изменение существенно влияет на layout;
- mobile.

Проверь:

- не появляется ли горизонтальный scroll;
- не выходят ли элементы за границы контейнера;
- остаётся ли текст читаемым;
- остаются ли кнопки и интерактивные элементы доступными;
- корректно ли перестраиваются flex/grid-контейнеры.

Не считай задачу завершённой, если новая функциональность работает только на desktop.

## 10. Доступность

По возможности используй семантически подходящие HTML-элементы.

Например:

- кнопку для действия;
- ссылку для навигации;
- корректный `label` для input.

Учитывай клавиатурную навигацию для интерактивных элементов.

Не создавай кликабельный `div`, если можно использовать `button` или `a`.

Для иконок без текста при необходимости добавляй понятный accessible label.

## 11. Маршрутизация

Если задача затрагивает React Router:

- сначала изучи существующую конфигурацию маршрутов;
- следуй используемому в проекте подходу;
- не создавай второй независимый способ организации routing;
- учитывай существующие вложенные маршруты;
- проверь прямое открытие новой страницы по URL;
- проверь переходы назад и вперёд в браузере, если изменение влияет на навигацию.

Не меняй существующие URL без прямой необходимости.

## 12. Обработка состояний интерфейса

Если функциональность работает с асинхронными данными, подумай о состояниях:

- loading;
- error;
- empty;
- success.

Не показывай пустой экран во время загрузки, если пользователю требуется обратная связь.

Если произошла ошибка, пользователь должен понимать, что действие не выполнено.

Не скрывай ошибку без обработки.

## 13. Производительность

Не выполняй преждевременную оптимизацию.

Не добавляй автоматически:

- `React.memo`;
- `useMemo`;
- `useCallback`.

Используй их только тогда, когда есть реальная причина:

- дорогостоящее вычисление;
- большой компонент с подтверждённой проблемой rerender;
- необходимость стабильной ссылки для memoized child;
- зависимость другого hook от стабильной ссылки.

Сначала выбирай понятный код.

## 14. Чего следует избегать

Избегай:

- несвязанного с задачей рефакторинга;
- новых зависимостей без необходимости;
- дублирования существующих компонентов;
- использования `any` без причины;
- ненужных `useEffect`;
- преждевременной мемоизации;
- изменения публичного API компонентов без необходимости;
- массового форматирования несвязанных файлов;
- архитектурных изменений, которые не требуются для решения задачи;
- усложнения решения ради потенциального будущего использования.

## 15. Проверка UI

После реализации проверь:

- основное пользовательское действие;
- loading state, если применимо;
- error state, если применимо;
- empty state, если применимо;
- desktop layout;
- mobile layout;
- корректность ссылок и кнопок;
- отсутствие очевидных визуальных регрессий.

Если какую-либо часть невозможно проверить автоматически, укажи это в итоговом отчёте.

## 16. Проверка кода

После реализации запусти:

```bash
npm run lint
npm run build
```

Если существуют тесты, непосредственно относящиеся к изменённой функциональности, запусти также их.

Если команда завершается ошибкой:

1. изучи ошибку;
2. определи, связана ли она с текущими изменениями;
3. исправь проблемы, вызванные текущей задачей;
4. повторно запусти проверку.

Не исправляй большое количество старых несвязанных ошибок без отдельного запроса.

## 17. Просмотр изменений

Перед завершением задачи просмотри итоговый diff.

Проверь:

- нет ли случайно изменённых файлов;
- нет ли лишнего форматирования;
- не осталось ли отладочного кода;
- не осталось ли `console.log`;
- не добавлены ли временные значения;
- не появились ли секреты или токены;
- соответствует ли реализация первоначальной задаче.

Если задача могла быть решена существенно меньшим количеством изменений, оцени, можно ли упростить реализацию.

## 18. Завершение задачи

После выполнения кратко сообщи:

- что было реализовано;
- какие основные файлы изменены;
- какие важные решения были приняты;
- были ли добавлены новые файлы;
- были ли добавлены зависимости;
- какие проверки были запущены;
- успешно ли прошли `lint` и `build`;
- что желательно проверить вручную;
- остались ли ограничения или потенциальные проблемы.

Не перечисляй каждую изменённую строку.

Сосредоточься на результате и важных технических решениях.
