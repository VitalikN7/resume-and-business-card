# Проект

Это персональный сайт-резюме и сайт-визитка.

Технологический стек:

- React 19
- TypeScript
- Vite
- Material UI
- React Router

Используй `npm` в качестве пакетного менеджера.

# Общие правила

- Перед внесением изменений сначала изучи существующий код, связанный с задачей.
- Следуй текущей структуре проекта и существующему стилю написания кода.
- Предпочитай изменять и переиспользовать существующие компоненты вместо создания лишних абстракций.
- Компоненты должны оставаться небольшими, понятными и отвечать за ограниченную область ответственности.
- Используй типы TypeScript и избегай `any`, если для него нет действительно веской причины.
- Переиспользуй существующие компоненты Material UI и стили проекта.
- Не добавляй другие UI-библиотеки или CSS-фреймворки без прямого указания.
- Не выполняй рефакторинг кода, который не относится непосредственно к текущей задаче.
- Сохраняй существующее поведение приложения, если задача явно не требует его изменения.
- Не создавай новые зависимости без необходимости.
- Перед добавлением новой библиотеки сначала проверь, нельзя ли решить задачу средствами уже используемого стека.
- Не усложняй архитектуру без необходимости.
- Выбирай наиболее простое решение, которое соответствует существующей архитектуре проекта.

# React

- Используй функциональные компоненты и React Hooks.
- Не используй class components.
- Избегай лишнего состояния.
- Если значение можно вычислить из существующих `props` или `state` во время рендера, не создавай для него отдельный `state`.
- Не используй `useEffect` для вычислений, которые можно выполнить непосредственно во время рендера.
- Используй `useEffect` преимущественно для синхронизации с внешними системами: API, браузерными событиями, таймерами, подписками и другими побочными эффектами.
- Для эффектов, подписок, таймеров и других внешних ресурсов обязательно выполняй очистку, если она необходима.
- Не используй `useMemo` и `useCallback` без необходимости.
- Добавляй мемоизацию только тогда, когда она решает реальную проблему производительности или необходима для стабильности ссылок.
- Используй стабильные идентификаторы в качестве `key` элементов списка.
- Не используй индекс массива как `key`, если список может изменяться, сортироваться, дополняться или удаляться.
- Не мутируй React state напрямую.
- При изменении объектов и массивов создавай новые ссылки.
- Не создавай лишние wrapper-компоненты и дополнительные уровни вложенности без необходимости.
- Если логика компонента становится слишком большой, рассмотри возможность вынести её в отдельный hook или компонент.

# TypeScript

- Сохраняй строгую типизацию.
- Не отключай проверки TypeScript без серьёзной причины.
- Используй явные типы для бизнес-сущностей, props компонентов и структур данных.
- Предпочитай `unknown` вместо `any`, если тип значения заранее неизвестен.
- Перед использованием значения типа `unknown` выполняй проверку или narrowing.
- Не используй `as` только для того, чтобы скрыть ошибку TypeScript.
- Type assertion допустим только тогда, когда тип невозможно корректно вывести другим способом и разработчик действительно знает больше, чем TypeScript.
- Переиспользуй существующие типы вместо создания одинаковых или почти одинаковых интерфейсов.
- Используй utility types, такие как `Pick`, `Omit`, `Partial`, `Record`, если новый тип является производным от существующего.
- Для сложных состояний предпочитай discriminated unions, если это делает состояние более безопасным и понятным.
- Не создавай чрезмерно сложные generic-типы без реальной необходимости.
- Типизация должна улучшать читаемость и безопасность кода, а не усложнять его.

# UI

- В первую очередь используй существующие компоненты Material UI.
- Не создавай собственный компонент, если аналогичный компонент уже есть в Material UI или внутри проекта.
- Сохраняй существующий визуальный стиль сайта.
- Не выполняй масштабный редизайн без явного запроса.
- Все изменения интерфейса должны корректно работать как минимум на desktop и mobile.
- Учитывай адаптивность при добавлении новых элементов.
- Старайся использовать существующие размеры, отступы, typography и другие UI-паттерны проекта.
- Не добавляй произвольные стили, если аналогичные значения уже используются в теме или существующих компонентах.
- Интерактивные элементы должны визуально показывать своё состояние.
- Кнопки, ссылки и другие элементы управления должны иметь понятное назначение.
- По возможности учитывай базовую доступность: клавиатурную навигацию, корректные HTML-элементы и понятные подписи.

# Архитектура и структура проекта

- Перед созданием нового файла проверь, нет ли уже подходящего места или аналогичной реализации.
- Следуй существующей структуре директорий.
- Не перемещай большое количество файлов без необходимости.
- Не меняй публичный API существующих компонентов без причины.
- Если изменение публичного API необходимо, проверь все места его использования.
- Избегай циклических зависимостей.
- Старайся сохранять направление зависимостей простым и понятным.
- Не смешивай бизнес-логику, отображение и работу с внешними системами в одном большом компоненте, если их можно разумно разделить.
- Общую логику выноси только тогда, когда она действительно переиспользуется или существенно улучшает читаемость.

# Работа с данными

- Перед добавлением нового состояния определи, где оно должно находиться.
- Не помещай локальное состояние компонента в глобальное хранилище без необходимости.
- Не дублируй одни и те же данные в нескольких местах без причины.
- Если данные можно вычислить из существующего состояния, предпочитай вычисление вместо дополнительного хранения.
- При работе с асинхронными данными учитывай состояния загрузки, ошибки и отсутствие данных.
- Не скрывай ошибки без обработки.
- Пользователь должен получать понятную реакцию интерфейса на ошибку, если она влияет на его действия.

# Производительность

- Не выполняй преждевременную оптимизацию.
- Сначала выбирай понятную и корректную реализацию.
- Оптимизируй только те участки, где существует реальная или очевидная проблема.
- Избегай ненужных повторных запросов.
- Не выполняй тяжёлые вычисления на каждом рендере, если они действительно дорогостоящие.
- Не добавляй `memo`, `useMemo` и `useCallback` автоматически.
- При работе с большими списками учитывай необходимость пагинации, lazy loading или виртуализации, если это действительно требуется.

# Рабочий процесс

Для нетривиальных задач используй следующий порядок работы:

1. Сначала изучи относящиеся к задаче файлы.
2. Определи существующую архитектуру и используемые подходы.
3. Перед внесением изменений кратко опиши предполагаемую реализацию.
4. Определи, какие файлы потребуется изменить.
5. Вноси минимальный набор изменений, необходимый для решения задачи.
6. Не изменяй несвязанный с задачей код.
7. После реализации самостоятельно просмотри получившийся diff.
8. Проверь, не появились ли лишние изменения.
9. Запусти необходимые проверки.
10. Исправь ошибки, появившиеся в результате внесённых изменений.

Для маленьких и очевидных изменений подробный план не требуется.

# Проверка изменений

После изменения кода запусти:

```bash
npm run lint
npm run build
```

Если в проекте имеются дополнительные тесты, относящиеся к изменённой функциональности, запусти также их.

Если какая-либо проверка завершается ошибкой:

- определи, связана ли ошибка с внесёнными изменениями;
- исправь ошибки, вызванные текущей задачей;
- не исправляй большое количество старых несвязанных проблем без отдельного запроса.

Не считай задачу полностью завершённой, если внесённые изменения приводят к ошибкам TypeScript, ESLint или сборки.

Если проверку невозможно выполнить, явно сообщи об этом и объясни причину.

# Работа с существующим кодом

- Не переписывай работающий код только потому, что существует другой способ его написать.
- Учитывай стиль и подходы, которые уже используются в проекте.
- При работе с legacy-кодом предпочитай постепенные и безопасные изменения.
- Не выполняй большой рефакторинг одновременно с добавлением новой функциональности без необходимости.
- Если обнаружена сторонняя проблема, которая не мешает текущей задаче, сообщи о ней отдельно вместо автоматического исправления.
- Сохраняй обратную совместимость, если иное не указано в задаче.

# Работа с зависимостями

- Не добавляй новые npm-пакеты без необходимости.
- Перед добавлением зависимости проверь, нельзя ли решить задачу существующими средствами.
- Если новая зависимость действительно необходима, объясни причину её добавления.
- Не обновляй версии существующих зависимостей без отдельной необходимости.
- Не изменяй lock-файл без причины.
- Не заменяй используемую библиотеку другой только из-за личных предпочтений.

# Безопасность

- Не добавляй в repository пароли, токены, API-ключи и другие секреты.
- Не записывай секретные значения непосредственно в исходный код.
- Используй переменные окружения для конфигурации, которая не должна находиться в коде.
- Не выводи чувствительную информацию в console.
- При работе с пользовательским вводом учитывай необходимость валидации.
- Не отключай механизмы безопасности браузера или библиотек ради упрощения реализации.

# Git и изменения файлов

- Не изменяй файлы, которые не относятся к текущей задаче.
- Не выполняй массовое форматирование всего проекта без необходимости.
- Не создавай commit автоматически, если пользователь явно об этом не попросил.
- Не выполняй push в remote repository без явного указания пользователя.
- Перед завершением задачи просмотри список изменённых файлов и убедись, что там нет случайных изменений.

# Завершение задачи

После выполнения задачи кратко сообщи:

- что было изменено;
- какие основные файлы были изменены;
- какие архитектурные или технические решения были приняты;
- какие проверки были выполнены;
- прошли ли `lint` и `build`;
- требуется ли что-либо проверить вручную;
- остались ли известные ограничения или потенциальные проблемы.

Не перечисляй каждое небольшое изменение построчно. Сосредоточься на важных изменениях и результате.
